# 개인 공통 작업 규칙

## 적용 범위

이 문서는 환경에 관계없이 공통으로 참고할 개인 작업 규칙의 정본이다. 시스템·조직의 상위 지침을 대체하지 않으며, 저장소별 작업에는 해당 저장소의 지침을 함께 따른다.

## 저장소 지침 탐색

- 작업 전에 저장소 루트의 `AGENTS.md`와 `.Codex/AGENTS.md`를 확인한다.
- `AGENTS.md`가 없으면 `AGENT.md`, `agents.md`, `agent.md`도 확인한다.
- 규칙 파일이 다른 정본을 참조하면 참조 대상까지 읽는다.
- 작업 대상 하위 디렉터리에 별도 지침이 있으면 해당 범위에 적용한다.
- 단일 정본을 지정한 저장소에서는 규칙을 복제하지 않고 얇은 참조 파일을 유지한다.
- 필수 지침은 먼저 확인한다. 같은 에이전트 맥락에서 이미 읽은 동일 버전의 문서는 재독보다 필요한 부분을 참조한다. 새 에이전트는 자신의 필수 지침을 확인한다.
- 조사는 답해야 할 질문과 대상 경로에서 시작한다. 조사 에이전트에 맡길 때는 필수 질문·대상 경로·제외 범위·중단 조건을 요청에 담는다. 답과 근거를 확보하면 마치고, 범위 확대가 필요하면 이유와 미확인 부분을 주 세션에 반환한다. 짧은 조사에 별도 계획이나 보고서를 형식적으로 만들지 않는다.
- 기능·스킬·설정이 없거나 비활성이라고 결론내리기 전에는 관련 Git 추적 목록, 숨김·무시 경로, 심볼릭 링크와 대상, 실제 로더 설정과 추가 탐색 경로를 확인한다. 파일의 존재·등록·실제 로드를 구분하고, 확인한 경로와 근거를 결론에 붙인다. 접근할 수 없거나 조사 범위가 제한되면 그 범위에서 미발견 또는 확인 불가로 보고한다.

## 작업 방식의 발전

- 사용자가 설명하는 실제 작업 방식을 바탕으로 규칙을 발전시킨다.
- 개선점이나 새로운 에이전트 작업 방법은 적용 효과와 비용을 설명하고 함께 논의한다.
- 제안이나 실험을 사용자와 합의된 상시 규칙으로 취급하지 않는다.

## 계획 우선 개발

- 개발 요구사항을 받으면 [계획 거버넌스](governance/planning.md)의 분기 기준으로 간소/정식 계획 경로를 선택한다. 정식 경로는 구현 전에 검토 가능한 계획 문서를 작성하고, 간소 경로는 짧은 접근 설명과 필요한 검사로 진행한다.
- 기존 코드와 전체 기획을 해치지 않는지, 요구사항을 만족하는지, 개선할 부분이 있는지 사용자와 검토하고 필요에 따라 여러 차례 수정한다.
- 정식 경로에서는 계획 검토와 구현 착수를 구분하며, 사용자가 구현 진행을 지시하기 전에는 계획 작성·보완에 집중한다.
- 정식 계획 작업에는 식별 번호를 붙이고, 실행 순서는 문서 내부의 의존성을 따른다. 선행 작업을 마친 뒤 후속 작업을 진행한다.

## 계획 거버넌스 적용

- 작업 경로 선택, 계획 작성·수정·검토 및 계획에 따른 구현 착수 전에 [계획 거버넌스](governance/planning.md)를 반드시 읽는다. 상세 정책은 해당 문서에만 유지한다.
- 계획 검토자는 메타데이터·리비전·전체 관계와 의미상 정합성을 필수 검사한다. 검토 결과는 대상 ID·버전과 연결한다.
- 정식 경로의 주 세션은 구현 착수 직전에 현재 계획·상위 버전·의존성과 검토 대상이 여전히 일치하는지 확인한다. 불일치하면 이전 검토를 재사용하지 않고 재검토를 요청한다.
- 필수 거버넌스나 원본을 읽지 못하면 누락을 알리고 해당 계획의 적합성을 확인했다고 보고하지 않는다.

## 작업 브랜치와 로컬 커밋

- Plan(P)별로 작업 브랜치를 두고 같은 Plan에 속한 Task(T)는 해당 브랜치에서 진행한다. PR을 만들 때도 Plan을 기본 범위로 삼는다. 상위 Plan이 없는 독립 Task는 자체 작업 브랜치를 사용한다. 간소 경로는 작업 단위의 브랜치를 사용하며, 브랜치를 위해 계획 문서나 ID를 형식적으로 만들지 않는다.
- 구현 착수 전 현재 브랜치와 미커밋 변경을 확인하고, 해당 작업 브랜치가 있으면 재사용하고 없으면 기준 코드를 확인해 생성한다. 다른 작업의 브랜치나 미커밋 변경을 섞거나 잃지 않으며, 기존 브랜치를 강제로 교체하거나 이력을 재작성하지 않는다.
- Task를 커밋 분할의 출발점으로 삼되 Task 수와 커밋 수를 일치시키지 않는다. 함께 설명·검증하고 되돌릴 수 있는 작은 Task는 묶고, 큰 Task는 검증 가능한 변경 단위로 나눈다. Plan 전체를 한 커밋으로 고정하지 않는다. 별도 검토 Task가 있어도 검토한 구현 변경과 함께 커밋할 수 있다.
- 구현·필요한 검사·해당 경로에서 요구하는 검토와 지적 처리를 마친 변경 단위로 로컬 커밋한다. 지적 처리는 수정 또는 근거 있는 미반영 판단과 필요한 재검토를 포함한다.
- 독립적으로 설명·검증하고 되돌릴 수 있는 변경은 나눠 커밋한다. 전체 작업 종료까지 변경을 누적하지 않는다. 커밋 전 diff와 스테이징 내용을 확인하여 해당 단위의 변경만 포함하고, 사용자의 기존 변경이나 다른 작업의 변경을 섞지 않는다.
- 커밋 메시지는 함께 보는 사람이 문제와 변경 내용을 이해할 수 있게 작성하며 개인 계획 ID나 로컬 기록 경로를 넣지 않는다. 계획과 커밋 해시의 연결은 [메모리 작성 거버넌스](governance/memory-writing.md)에 따라 로컬 기록에 남긴다.
- 승인된 구현 범위의 로컬 커밋은 별도 지시를 기다리지 않고 수행한다. 푸시·PR 생성·배포는 사용자가 명시적으로 지시한 범위에서 수행한다. 상위·저장소 지침과 실제 도구 권한을 따르며, 커밋할 수 없으면 이유와 남은 미커밋 범위를 보고한다.

## 프로젝트 공유 작업 메모리

- 메모리는 세션별이 아니라 프로젝트별로 공유한다. coding·infra 등 순차적으로 사용하는 서로 다른 세션도 같은 기록으로 맥락을 이어받는다.
- Git 레포 루트의 로컬 `.harness/`에 아래 구조를 사용한다. 생성·Git 제외·충돌 처리는 [계획 거버넌스](governance/planning.md)의 위치 규칙을 따른다.

```text
.harness/
  plans/                    # 작업별 폴더, [done]- 완료 표시
    <작업명>/               # S/P/T, S가 있으면 index.md
      history/              # 이전 계획 revision 원문
  memory/
    current.md              # 현재 맥락과 재개 지점
    progress/
      T03.md                # 계획 ID별 실제 진행 요약
    history/                # 작업·결정·문제 해결의 원본 이력
```

- 계획은 앞으로 할 일을, 메모리는 실제 진행과 판단을 기록한다. `progress/`에는 계획서를 복제하지 않는다.
- 모든 세션은 시작 시 `current.md`를 읽고, 관련 계획과 `progress/` 기록을 확인한다. 상세 맥락이 필요하거나 사용자가 질의하면 연결된 `history/` 원본을 찾아 읽는다.
- 요약과 이력을 읽을 때 관련 계획 ID·버전과 코드 상태를 확인하여 어느 시점의 판단인지 구분한다.
- 역할이 다른 세션도 프로젝트 공통 요약의 결정·제약·위험을 확인한다. 세션만의 기억에 의존하지 않는다.

### 메모리와 현재 상태의 대조

- 세션 시작 시 메모리에 기록된 기준 계획 버전과 코드 상태를 현재 계획·코드 상태와 대조한다. 코드 상태에는 브랜치·커밋뿐 아니라 관련 미커밋 변경도 포함한다.
- 불일치하면 메모리를 그대로 신뢰하거나 현재 상태를 메모리에 맞춰 덮어쓰지 않는다. 관련 계획·코드·원본 이력을 확인하여 변경 내용을 파악한 뒤 진행 기록과 현재 요약을 갱신한다.
- 확인할 수 없는 내용은 불확실성으로 표시하고, 확인된 사실이나 확정 결정으로 취급하지 않는다.
- 메모리는 재개를 위한 안내이며 현재 계획과 코드 상태를 대신하는 정본이 아니다. 이 대조는 맥락 복원 절차로서 구현 검증이나 최종 완료 판정을 대신하지 않는다.

### 메모리 작성 거버넌스 적용

- 정식 경로의 의미 있는 작업 진행, 중요한 결정·계획 변경·문제 해결, 세션 종료·전환 시 메모리를 갱신한다. 간소 경로는 메모리 작성 거버넌스의 최소 기록 기준을 따른다. 구현 없이 결정만 이루어진 경우도 포함한다.
- 현재 상태 대조에서 불일치를 확인하여 기록을 정정하거나, 길어진 요약을 압축할 때도 작성 거버넌스를 적용한다.
- 메모리 작성·수정·압축 전에 [메모리 작성 거버넌스](governance/memory-writing.md)를 반드시 읽는다. 상세 작성·집계·원본 보존 정책은 해당 문서에만 유지한다.
- 필수 작성 거버넌스를 읽지 못하면 제약을 알리고 메모리를 갱신했다고 보고하지 않는다.

## 독립 검토와 조율

- 주 세션은 계획 작성·구현·검토 호출·수정·사용자 보고를 조율한다. 구현자 전용 역할 파일은 현재 필수로 두지 않는다.
- 하위 에이전트의 결과와 백그라운드 알림은 주 세션이 통합한다. 같은 상태를 반복 보고하지 않고 새 발견·결정·차단 조건이 있을 때 갱신한다. 사용자가 상태를 물으면 현재 상태를 간결하게 답한다.
- 계획 검토와 구현 결과 검토는 별도 역할과 새 에이전트 맥락에서 수행한다. 같은 세션에서 역할 파일만 읽는 것은 독립 검토로 취급하지 않는다.
- 주 세션은 하네스 루트의 역할 파일과 필요한 원본 자료를 전달한다. 전체 대화나 구현자의 결론을 그대로 상속하기보다 요구사항과 결정된 제약, 관련 미결 사항을 전달한다.
- 정식 경로에서 사용자에게 계획 검토를 요청하기 전에 [계획 검토자](../agents/plan-reviewer.md)를 호출한다. 지적을 반영하거나 미해결 쟁점으로 명시한 계획과 검토 결과를 함께 제시한다.
- 정식 경로는 구현자가 변경에 적합한 검사·테스트를 수행한 뒤 [결과 검토자](../agents/implementation-reviewer.md)를 호출한다. 간소 경로의 결과 검토 여부는 계획 거버넌스의 기준을 따른다. 실행하지 못한 검사는 이유와 함께 전달하며 통과한 것으로 취급하지 않는다.
- 결과 검토를 수행하는 경우 주 세션은 구현 전 예상 검토 모드를 정하고 구현 후 변경 위험에 맞춰 최종 조정한다. CODE/RUN/ENV의 상세 기준은 결과 검토자 역할 파일을 따르며 범위·계획 버전·코드 기준·검사 항목·환경·허용 행위를 검토 요청서로 전달한다.
- 검토 범위가 넓어져도 권한을 일괄 확대하지 않는다. 주 세션이 필요한 도구와 환경을 준비하고, 직접 접근이 불가능하면 검사 결과 원본을 전달한다. 검토자는 미확인 범위와 근거 출처를 구분한다.
- 결과 검토자는 하나로 시작한다. 분야별 병렬 검토를 도입할 때는 동일한 코드 기준을 공유하고 주 세션이 결과를 통합한다.
- 검토자는 원본을 읽고 근거 있는 지적을 반환한다. 계획·코드·공유 메모리를 직접 수정하지 않는다. 검사 실행은 허용된 환경과 권한 범위에서 수행하고 생성 산출물은 소스 수정과 구분한다.
- 주 세션은 지적의 근거를 확인하고 수정 또는 미반영 이유를 기록한다. 중요한 수정은 영향받은 검사와 독립 재검토를 수행한다. 계획 방향 변경은 기존 무효화 절차를 따른다.
- 리뷰어의 판단은 사용자 승인이나 실제 실행 검증을 대체하지 않는다. 문제 미발견과 결함 부재를 동일하게 취급하지 않는다.
- 검토 범위, 계획 ID·버전, 코드 기준과 미커밋 변경, 검사 결과, 지적 처리와 미확인 범위를 공유 메모리에 연결한다. 검토 후 대상이 바뀌면 이전 결과를 새 상태의 검토 결과로 재사용하지 않는다.
- 새 에이전트를 실행할 수 없거나 역할 파일·필수 원본을 읽지 못하면 제약을 알리고 독립 검토 미수행으로 표시한다. 자체 검토를 독립 검토로 보고하지 않는다.
- 역할 파일은 도구 독립적인 지침이다. 자동 등록·호출 기능이 구현되었다고 가정하지 않는다. 분야별 병렬 검토와 구현 작업 분배 정책은 추후 정한다.

계획 상세 정책과 메모리 작성 정책은 각각 별도 거버넌스에 유지한다. 나머지 정책의 추가 분리는 전체 내용과 사용 흐름을 확인한 뒤 결정한다.
