# 계획 거버넌스

계획 작성·수정·검토·구현 착수 시 적용하는 상세 정책의 정본이다. [공통 규칙](../AGENTS.md)과 함께 따른다.

## 작업 경로 선택

- 관련 코드를 짧게 조사한 뒤 아래 조건을 모두 만족하면 간소 경로를 선택한다. 파일 종류·줄 수·파일 수·예상 시간만으로 결정하지 않는다. 조사 자체는 계획 문서 작성의 사유가 아니다.
  1. 원하는 결과와 완료 조건이 명확하다.
  2. 구현 방향이 하나로 좁혀져 사용자에게 선택받을 설계 대안이 없다.
  3. 영향이 제한되고 기존 공개 인터페이스·공유 설정·운영 상태를 바꾸지 않는다.
  4. 직접 확인이나 제한된 검사로 요구 충족을 판단할 수 있다.
  5. 기존 데이터 손실 없이 쉽게 되돌릴 수 있다.
- 간소 경로는 접근 방식과 선택 이유를 짧게 설명 → 구현 → 필요한 검사 → 결과·한계 보고로 진행한다. 별도 S/P/T 문서·ID·작업 폴더와 독립 계획 검토를 요구하지 않는다. 사용자의 구현 요청이 있으면 별도 계획 승인을 반복해서 요청하지 않는다.
- 간소 경로의 독립 결과 검토는 데이터·인증 상태 보호 등 오류 영향이 큰 부분에 불확실성이 남으면 수행한다. 그렇지 않으면 구현자의 필요한 검사로 마친다. 검토가 불확실성을 해소하지 못하면 완료를 단정하지 않는다.
- 요구 해석·설계 선택이 필요해지거나 영향이 여러 구성 요소로 확대되거나 데이터·권한·배포·공유 인터페이스 변경이 필요하거나 완료 검사 방법이 불명확해지면 추가 구현을 멈추고 정식 계획 경로로 전환한다. 이미 한 변경·검사와 전환 이유를 기록하고 필요한 S/P/T 깊이를 선택한다. 불명확한 조건은 간소 경로 충족으로 간주하지 않는다.
- 정식 계획 경로는 아래 계층·독립 계획/결과 검토 절차를 따른다. 간소 경로도 대상 저장소 지침과 실제 도구 권한·승인 조건을 따른다.

## 계획 문서의 계층

복잡하거나 처음부터 구상하는 작업은 다음 계층으로 구분한다. 작업 규모에 맞게 문서를 나누며, 모든 작업에 세 문서를 일률적으로 요구하지 않는다.

| 계층 | 답해야 하는 질문 | 주요 내용 |
| --- | --- | --- |
| 최상위 기획서 | 왜 만들고, 무엇을 달성하는가? | 개념, 문제, 목적, 범위와 제외 범위 |
| 큰 틀의 계획서 | 어떤 구조와 단계로 해결하는가? | 기존 코드와의 관계, 구성 요소, 단계와 의존성 |
| 상세 코드 작성 계획서 | 이번 작업에서 무엇을 어떻게 바꾸는가? | 변경 대상, 동작과 인터페이스, 구체적인 구현 순서 |

- 하위 계획서는 상위 문서를 참조하고, 상위 목적·범위·방향과 일치하도록 작성한다.
- 상위 방향과 충돌하거나 변경이 필요하면 이를 명시하고 사용자와 해당 문서를 함께 보완한다.

### 작업 영향에 따른 계층 선택

- T만 작성: 원인과 수정 범위가 명확한 국소 버그 수정이나 간단한 변경.
- P → T 작성: 사용자 흐름, 기존 코드와 여러 구성 요소의 상호작용을 고려해야 하는 변경.
- S → P → T 작성: 개념·목적·범위·한계부터 판단해야 하는 대형 변경이나 새로운 방향 결정이 필요한 신규 기능.
- 급한 작업도 영향이 넓으면 P를 작성한다. 기존 패턴을 따르는 작은 신규 기능은 S를 생략할 수 있다.
- P 작성 시 기존 코드를 조사하고 참고 파일의 역할, 인터페이스·호출 흐름, 유지해야 할 제약을 기록한다. 확인된 사실과 가정을 구분하고 T 작성의 근거로 삼는다.
- T만 작성하는 경우에도 직접 관련된 코드를 확인하고 조사 근거를 T에 간략하게 기록한다.

## 계획 문서의 식별과 관계

| 기호 | 의미 | 역할 |
| --- | --- | --- |
| S | Spec | 개념·목적·범위를 담는 최상위 기획서 |
| P | Plan | 구조·단계를 정하는 큰 틀의 계획서 |
| T | Task | 실행 가능한 작업 단위의 상세 코드 작성 계획서 |

- 제목은 `[S01] 공통 규칙 배포`, `[P01] 설치 방식 설계`, `[T03] 백업 구현`처럼 `[ID] 주제`로 작성한다.
- ID는 프로젝트 안에서 기호별로 중복 없이 부여하고, 번호는 두 자리부터 시작한다. 번호는 식별자이며 계층 관계나 실행 순서를 인코딩하지 않는다.
- 파일명은 `S01-rule-distribution.md`, `P01-installation.md`, `T03-backup.md`처럼 제목의 ID와 일치시킨다.
- 상위 계획이나 실행 순서가 바뀌어도 기존 ID는 유지한다.
- 문서 시작의 YAML front matter에 `id`, `revision`, `parent`, `parent_revision`, `depends_on`, `waiting_on`을 명시한다. 문서 참조 값은 대상 문서의 ID를 사용한다.
- `parent`는 직접 상위 문서의 ID이며, 상위 문서가 없으면 `null`로 표시한다. `depends_on`은 선행 작업 ID의 목록이며, 없으면 `[]`로 표시한다.
- `revision`은 1부터 시작하는 문서의 계획 버전이다. `parent_revision`은 작성·재검토의 기준이 된 상위 문서 버전이며, 상위 문서가 없으면 `null`로 표시한다.
- `waiting_on`은 권한 발급 등 외부 대기를 간략하게 적는 목록이며, 없으면 `[]`로 표시한다. 내부 작업 의존성과 구분한다.
- 상위 문서는 방향과 소속을, 선행 작업은 실행 제약을 나타낸다. 상위 문서를 자동으로 선행 작업으로 취급하지 않는다.
- T는 구현 코드 자체가 아니라 구현할 작업을 설명하는 계획 문서다.

예를 들어 다음 문서는 P01에 속하며 T01 이후에 진행한다. T02를 기다려야 한다는 의미는 아니다.

```yaml
---
id: T03
revision: 1
parent: P01
parent_revision: 2
depends_on: [T01]
waiting_on: []
---
```

의존성이 없다는 사실만으로 멀티에이전트 병렬 실행을 자동 승인하지 않는다. 멀티에이전트의 조율·실행 정책은 별도로 정한다.

## 계획 변경과 무효화

- 목적·범위·설계·인터페이스·의존성에 영향을 주는 변경은 `revision`을 올린다. 오탈자나 의미를 바꾸지 않는 설명 보완은 해당하지 않는다.
- 상위 방향 변경 시 계획 저장소의 해당 프로젝트 문서 전체를 확인하고 `parent` 관계를 재귀적으로 따라 모든 하위 계획을 찾는다. 영향이 없을 것이라는 추정으로 일부를 제외하지 않는다.
- S 변경 시 연결된 P·T 전체를, P 변경 시 연결된 T 전체를 무효화한다. 다른 독립 계획까지 무효화하지 않는다.
- 무효화는 파일 삭제가 아니라 이전 계획으로 실행하지 않는 것을 뜻한다. 이전 버전의 내용과 무효화 이유를 확인할 수 있도록 보존한다.
- 상위부터 하위 순서로 다시 작성하거나 재검토한다. 검토가 완료된 문서만 `parent_revision`을 갱신하고 실행 대상으로 복귀시킨다. 버전 숫자만 일괄 갱신하지 않는다.
- 구현 중 예상치 못한 발견으로 P를 수정할 때는 변경 전후·이유·영향을 남긴다. 연결된 T는 우선 무효화하고 재검토하여 수정 또는 재작성한다. S의 방향까지 바뀌면 구현을 멈추고 상위 기획부터 다시 검토한다.
- 실행 전에는 직접 부모부터 최상위까지 모든 `parent_revision`이 현재 상위 `revision`과 일치하는지 확인한다. 상위 중 하나라도 무효하면 해당 하위 계획으로 실행하지 않는다.
- 무효화된 작업에 의존하는 작업도 대기한다. 내부 선행 작업과 외부 대기가 해소되기 전에는 해당 작업을 진행하지 않는다.
- 순환 의존성은 만들지 않는다. 중복 ID, 누락된 참조, 상위 관계나 의존성의 순환이 발견되면 해당 관계에 따른 실행을 중단하고 먼저 계획을 정리한다.
- 이 규칙은 에이전트가 수행할 절차다. 자동 탐색·버전 검사 기능이 구현되었다고 가정하지 않는다.

## 작업 묶음과 이전 revision 보존

- 정식 계획은 `.harness/plans/<작업명>/`에 작업별로 묶는다. P와 하위 T는 같은 폴더에 두며 독립 T도 작업 폴더 하나를 사용한다. 새 작업에 기존 ID를 재사용하지 않는다. ID는 완료 폴더를 포함하여 프로젝트 전체에서 기호별로 고유하다.
- S 계층이 있으면 해당 작업 묶음 최상위에 `index.md`를 둔다. S/P/T 경로와 작업 묶음별 완료 여부를 안내하며 목적·설계·진행 내용을 복제하지 않는다. S가 없는 작업은 P 또는 독립 T가 진입점이며 index를 요구하지 않는다.
- 계획을 개정하기 전에 이전 원문을 해당 작업 폴더의 `history/<ID>-rev<N>.md`에 보존하고 변경 이유·영향·무효화 및 재검토 근거를 연결한다. 기존 보존본을 덮어쓰지 않는다. 이 history는 계획 보존본이며 실제 수행·결정 이력의 정본인 `.harness/memory/history/`와 구분한다.
- 작업 묶음 전체가 완료되면 폴더 이름에 `[done]-`을 붙인다. 완료 근거와 남은 검증 한계는 실제 진행 기록에 남기고 index가 있으면 안내도 갱신한다. 미완료 하위 작업이나 필수 대기가 남은 묶음은 완료로 표시하지 않는다. 미완료 폴더는 실행 가능·승인됨을 뜻하지 않는다. 추가 상태 파일이나 상태 열거 체계는 요구하지 않는다.
- 완료 표시로 경로를 변경할 때 계획·index·메모리의 링크와 경로 참조를 함께 갱신하고 깨진 참조가 없는지 확인한다. 과거 이력의 당시 판단은 바꾸지 않는다. 완료 작업을 다시 열면 접두사를 제거하고 동일하게 참조를 갱신한다.
- 현재 계획은 작업 폴더와 완료 폴더를 재귀 탐색하되 각 `history/`의 보존본과 `index.md`를 현재 S/P/T로 집계하지 않는다. 완료 표시는 삭제·ID 재사용·참조 제외의 근거가 아니다. 상세 본문은 관련 관계·변경 영향에 맞춰 읽되 전체 관계 검사를 생략하지 않는다.
- 기존 평면 plans 및 별도 history의 원본은 계속 읽고 보존한다. 새 구조로 자동 이동·재번호 부여하지 않는다. 이동이 필요하면 참조를 함께 정리하고 복제 정본을 남기지 않는다.

```text
.harness/plans/
  document-upgrade/
    P01-document-upgrade.md
    T02-renderer.md
    history/P01-rev1.md
  [done]-local-launcher/
    T01-local-launcher.md
    history/T01-rev1.md
```

## 로컬 계획·메모리 위치와 Git 관리

- 프로젝트 계획·메모리의 정본은 코드 레포 루트의 `.harness/`에 둔다. `plans/`, `memory/current.md`, `memory/progress/`, `memory/history/`로 구분한다.
- 작업 시작 시 Git 레포 루트를 확인하고 `.harness/plans/`의 작업 묶음·완료 표시와 현재 계획 전체의 관계를 확인하고 대상 계획·관련 메모리를 읽는다. 다른 위치에 복제 정본을 만들지 않는다.
- `.harness/`는 개인 로컬 작업 공간이다. 공유 `.gitignore` 대신 `git rev-parse --git-path info/exclude`가 가리키는 로컬 제외 파일에 `/.harness/`를 등록한다. worktree에서는 `.git`이 디렉토리라고 가정하지 않는다.
- 생성 전에 해당 경로의 기존 파일·심볼릭 링크·추적 여부를 확인한다. 이미 추적된 파일은 ignore로 숨길 수 없으므로 자동 삭제·추적 해제하지 않고 충돌을 사용자와 해결한다.
- `.harness/`를 커밋·푸시·릴리스 패키지에 포함하지 않는다. 강제 추가하지 않으며 게시 전에 추적 목록과 패키지 내용을 확인한다.
- 공통 규칙·검토자 역할은 설치된 하네스에서 참조하고 공동 레포에 개인 등록 설정을 기본으로 추가하지 않는다.
- 계획에는 기준 코드의 브랜치·커밋과 관련 미커밋 변경을 명시한다. 다른 clone·환경으로 기록은 자동 전달되지 않는다. 백업·동기화 및 worktree 간 공유 방식은 후속 설계한다.
- 회사 관련 기록은 회사 관리 범위에 유지한다. 개인 공개 규칙 저장소에는 포함하지 않는다.

## 미완결 사항과 불확실성

- 기획서와 계획서의 마지막에 `미완결 사항 및 불확실성`을 둔다. 해당 사항이 없으면 없다고 표시한다.
- 아직 정하지 않은 내용, 확인이 필요한 가정, 사용자와 논의할 질문을 정리한다.
- 미결정 내용을 확정된 요구사항이나 설계처럼 취급하지 않는다.
- 사용자와 상호작용하며 답변과 결정 내용을 문서 본문에 반영하고, 해결된 항목은 미결 목록에서 정리한다.
- 다음 단계에 영향을 주는 미결 사항이 있으면 그 영향을 설명하고, 해결이 필요한 부분을 임의로 확정해 진행하지 않는다.
